# 决策记录（UI 扩展侧）

> 只记“为什么”，不记“做什么”。每条给编号，方便以后在代码注释里引用。

## D-U01 · 界面形态 = 右下角浮窗 + 抽屉

- **决定**：不占独立页面，不做全屏；右下角一个 48px 浮窗，点开是贴右侧的抽拉面板（宽 ≤ 360px）。
- **为什么**：UI 要“随时能看到、不打断叙事”；Z 纪事的痛点就是全屏遮挡。抽屉关掉后只剩一个角标，聊天界面回到原样。
- **代价**：屏幕窄时抽屉会盖住输入框右侧；手机竖屏体验一般。接受，P4 再做适配。

## D-U02 · 声明来源 = 手写/粘贴 JSON + 校验器（P1-P2），表单编辑器（P3 之后）

- **决定**：先让“能写出来”，再让“不用学语法”。
- **为什么**：JSON 是唯一真相，编辑器只是它的另一种输入法；先有稳定 schema，编辑器才有东西可编辑。反过来做会把 schema 锁死在表单里。
- **代价**：第一版用户必须看示例；校验器必须给出“第几个控件、哪一行”级别的错误，否则手写体验崩。

## D-U03 · 布局库存储位置 = 可选（全局 或 绑定角色卡），默认全局

- **决定**：每条布局带 `scope: "global" | "character"`，`character` 时记录 `avatar`。加载时先找与当前聊天角色同 avatar 的，找不到再用全局默认。
- **为什么**：两种使用方式都真实存在——通用面板（行动按钮、状态）和角色专属面板（酒馆、战棋）。写死一种都会逼用户换扩展。
- **代价**：导入/导出要处理“当前没有角色卡”的情况；P1 先把字段留好，P3 才实现切换。

## D-U04 · 点击的默认效果 = 只改变量，下一轮提示词自然带到

- **决定**：`set` / `add` 直接调 `ILB.api`；**不**调 `generate`、**不**碰 prompt 构建。
- **为什么**：ILB 的边界就是“变量是接口”（`docs/UI扩展接口.md` §3）；UI 一旦学会触发生成，就会和“判定轮次”“注入预算”打架，而且用户会失去对叙事的控制。
- **代价**：点完按钮界面立刻变，但故事要等下一轮。这正是想要的——点一下按钮 ≠ 让 AI 立刻说话。

## D-U05 · `area` 从 0 开始

- **决定**：`[col, row, colSpan, rowSpan]`，行列都从 0 数。
- **为什么**：和 CSS Grid 的 `grid-column-start` 一致，渲染时直接 `gridColumn = col + 1`，不用在心算里到处 `-1`。两份旧文档曾经一个写 0 一个写 1，以此为准。
- **代价**：`docs/交接-UI扩展.md` 里要改一处（已列进《给ILB的问题清单》ILB-UI-10）。

## D-U06 · 渲染分两层：纯函数出计划，DOM 只负责画

- **决定**：`plan.js` 输入 `(layout, vars)` 输出纯数据；`panel.js` 才碰 DOM。不用 `innerHTML`。
- **为什么**：布局来自用户粘贴的 JSON，`innerHTML` 等于开放注入；纯函数让“哪些格子该显示、文字怎么格式化”可以在 Node 里直接测，不用起浏览器。
- **代价**：多一层间接，改样式时要同时想 plan 里的 `tone`。

## D-U07 · 固定定位用视口高度算尺寸，不用 top+bottom 拉伸

- **决定**：抽屉高度写 `height: calc(100vh - …)`（后跟 `100dvh` 回退），浮窗位置写 `top: calc(100vh - …)`；不用 `bottom` 参与定位。
- **为什么**：ST 窄屏把 `body` 设成 `position: fixed`，`<html>` 高度变 0；页面里 `<html>` 又带单位 `transform`，于是它成了 `fixed` 后代的包含块——`top`+`bottom` 会相对 0 高度求解，抽屉塌成 2px、浮窗跑到视口上方（2026-10-25 竖屏崩溃的真因，详见《P1-完成记录》）。
- **代价**：`vh` 在旧版 iOS Safari 是“大视口”，底部可能有偏差；已用 `100dvh` 覆盖现代浏览器，旧机可接受。

## D-U08 · 不排除 ST 的 `html` transform，也不依赖它

- **决定**：不检测、不覆盖 `documentElement` 的 transform，只让自身布局与包含块无关。
- **为什么**：那个 transform 可能来自主题/别的扩展，跟着它做适配会被别人的升级拖垮；用 `vh` 算尺寸则两种包含块下都对。
- **代价**：如果以后 ST 把浮层放进有 transform 的容器，仍需复测（`tmp/shoot.mjs` 一条命令可验）。

## D-U09 · `add` 是 UI 侧的“读-算-写”糖，不是 ILB 接口动作

- **决定**：`onClick: { kind: "add", var, by }` 由 UI 用 `snapshot()` 读当前值、加完再用 `set` 写回；变量不存在时拒绝（不凭空创建）。ILB 侧不新增 `add` 动作。
- **为什么**：ILB 的接口动作只有 set/call（`docs/UI扩展接口.md` §5；接口 v1.1 也没有 add，见《给ILB的问题清单》ILB-UI-01）。但“金币 +1”是声明式 UI 最高频的交互，逼用户自己算新值等于逼用户记状态。api 是同步的，读和写之间不可能插入别的调用，所以“先读后写”在当前实现下是原子的。
- **代价**：如果 ILB 以后改了 snapshot 的语义（比如异步化），这层糖要重新评估；多逻辑并发写同一变量时，仍是“后写赢”。

## D-U10 · 布局作用域：键按“全局 / 角色卡”分开存，切换靠下拉框

- **决定**：`dshui.layouts.v2` 存全部布局（含 `scope` 与 `avatar`）；`dshui.selected.v2` 存每个作用域的选中 id；当前作用域由 `getAvatar()` 决定（无角色卡 → 全局）。
- **为什么**：用户明确要“可选，全局和角色卡”。把“选中哪套布局”与“布局存在哪”分开，才能做到同一个聊天里临时切到全局面板、又不动角色卡自己的默认。
- **代价**：角色卡删了，它名下的布局会留在库里、选不中（孤儿条目，P4 再做清理）。

## D-U11 · 兼容别名收在 `normalize*` 里，渲染与校验只认一种形状

- **决定**：`widgets`→`cells`、`type`→`kind`、`bind`→`var`、`action`→`onClick`、`items[].onClick` 与 `"step"`（number 控件）都在归一化时折叠成我们的形状。
- **为什么**：交接文档自己就同时用了两套名字（§2 的 schema 与 §6 的完整示例），两份旧文档又各写一套；让用户“写哪个都对”，但内部只有一条代码路径。
- **代价**：归一化不替用户改“真错”（比如 `area` 少一个数、`op` 拼错），这些仍交给校验器按用户原文的键名报错。

## D-U12 · 不做页面跳转，只做“动作”

- **决定**：P1-P2 不实现 `onClick: { kind: "goto" }` 之类的能力；跨面板导航留给 P5 的“页面”概念。组件里只有 `open`（调 ILB 的 `ui.openPanel`）算“跳转”。
- **为什么**：用户要的是“网格里点一下 → 改变量/调逻辑”，不是再造一个多页应用；页面会带来“当前页”“返回栈”“页间传参”一整套状态，和“UI 不负责逻辑执行”的定位冲突。
- **代价**：当前没有分页/标签页；如果 P4 发现玩法需要多页面（比如背包单独一页），要引入 `pages` 字段并设计返回规则，届时再记一条决策。
- **后续（D-U16）**：P4 真加了多页面，但只做“页签 + `open.page` 切换”，仍然没有返回栈；本条“不做 goto”依然成立。

## D-U13 · 导入导出用带 `kind` 的包裹对象，导入先进预览

- **决定**：导出文件与剪贴板内容都是 `{ kind: "dshui-ui", format: 1, layout: {...} }`；导入同时接受这个包裹和裸布局。`format > 1` 直接拒绝，`kind` 不认识只在“包裹形状”时报错。导入结果**只进预览**，不自动保存。
- **为什么**：裸布局没有“这是不是本扩展的文件、用的哪版格式”的线索；加一层两字段的信封，未来加字段（作者、时间、缩略图）不需要破坏老文件。导入不自动覆盖是防手滑——`localStorage` 里可能存着用户认真调过的面板。
- **代价**：用户多一步“保存”；导出不含 `avatar`（见 D-U14 的边界），换人导入要按对方当前角色卡保存。

## D-U14 · 表单编辑器只编辑“声明里有的字段”，不做能力发现

- **决定**：表单固定覆盖：标题、网格五项、页面（切页/增删）、每个控件的 `id/kind/area/label/text/var/items/format/onClick`、动作字段（`var/by/value/op/name/args/tab/page`）。控件类型用下拉，字段跟着类型显示；`list` 的条目用多行文本（每行 `文字 | 变量 | 步长 | 上限`）。
- **为什么**：用户不懂 JSON，表单是主入口；但 P3 的目标是“能改到自己会写的那一份”，不是给每个新控件造一个配置面板。固定字段 + 校验器兜底（表单存完仍走同一套 `validateLayout`），比引入“控件注册表”便宜得多。
- **代价**：接口以后加新控件类型，表单要手写一段；`list` 的条目编辑是文本协议，不是可视化行编辑。

## D-U15 · 失效布局只列不自动删

- **决定**：「管理布局」列出全局条目 + **当前**角色卡的条目，前者/后者都可删；别的角色卡的条目只显示名字与头像，不提供删除；不扫描全存档、不自动清理。
- **为什么**：删除是不可逆的（`localStorage` 无回收站），而“这个角色卡是不是真没了”很难判断——用户可能只是换了个聊天。列出来让用户自己删，比替他猜安全。
- **代价**：存档多了以后“别的角色卡”列表会变长；真要做“一键清理”，得先有“这个 avatar 在全存档里还存在吗”的扫描，那是下一步。

## D-U16 · 多页面用 `pages` 数组，只做页签 + `open.page`，不做返回栈

- **决定**：布局可写 `pages: [{ id, title, grid?, cells[] }]`（最多 12 页）；顶层仍是默认页，写法与旧单页兼容。切页只有两条路：点页签条，或别的控件 `onClick: { kind: "open", page: "..." }`。「返回」由作者自己放按钮，扩展不记来路。
- **为什么**：P4 要解决“内容多了一屏放不下”。页签 + 显式 `open` 是“声明式”的：当前页是 UI 状态，不写回变量，也不进 AI 上下文；返回栈会把 UI 变成有历史的交互程序，和“只负责展示与点击”的边界冲突。
- **代价**：作者要自己设计“返回”按钮；`open.page` 的目标必须存在（校验器会拦），页面 id 重复也会拦。

## D-U17 · 预览与编辑的高度：默认 50%，可拖动，双击复位

- **决定**：编辑态下编辑区固定高度（CSS 默认 `50%`，`min-height: 140px`），预览区 `flex: 1` 且自身滚动；两者之间放一个 12px 的拖动条，`pointer` 事件改编辑区内联高度，双击清空回默认；高度写 `dshui.ui.v1` 的 `editorHeight`，下次打开沿用。
- **为什么**：JSON 文本框天生 `flex: 1` 能占满，表单块却会缩在底部；但不同用户在不同屏幕上对“预览大还是表单大”的偏好相反，给一个默认值 + 可拖动，比猜一个固定比例好。拖动条同时兼容触屏（`touch-action: none`）。
- **代价**：多一个 `editorHeight` 存储字段；拖动状态不参与布局序列化（它属于界面偏好，不属于布局内容）。

## D-U18 · 侧边「把手」取代圆形浮球

- **决定**：收起态是 22×88 的贴边条，只露 12px（`right:-10px`），左侧圆角、右侧贴边；展开时 JS 按面板左缘定位（`z-index: 3999`，在面板 4000 之下），只露 12px，像抽屉拉手；点击开合，竖向拖动改高度并写 `dshui.ui.v1` 的 `handleY`；悬停时多露 6px。
- **为什么**：48px 圆球在聊天区右侧、输入栏上方会压住消息和滚动条；贴边条几乎不占视觉面积，仍能被发现和点击。展开时挂在面板边缘，既提示「可以收起」，也不额外占聊天区。
- **代价**：12px 热区较窄，拖动与点击要靠 4px 位移阈值区分；`handleY` 是视口坐标，换分辨率或横竖屏要重新 clamp。

## D-U19 · 把手避让，不接管其他悬浮球（本期）

- **决定**：只做避让——收起时扫描 `.ilb-fab` 的可见矩形，若与把手重叠，就把把手上移/下移一个 gap 让开；`maxHandleTop()` 还把把手限制在 `#send_form` 顶边之上。
- **为什么**：ILB 的球位置固定且已知，避让是纯几何运算、零风险；真正「接管」其他扩展的球要猜它们的 DOM 与点击语义，误判会让用户某个面板再也打不开。先把我们自己的遮挡问题解决，接管留到有失败记录与恢复入口之后再谈。
- **代价**：其他扩展的球仍可能与把手视觉相邻；两边都拖到同一高度时，只靠 8px 间隙区分。

## D-U20 控件类型只汉化“显示层”（0.5.0）

- 决定：界面上的类型下拉、控件列表、新增控件默认名一律显示中文（状态/文本/按钮/条形/数字/开关/列表）；存进 JSON 的 `kind` 仍是英文 key。
- 理由：JSON 要能分享、能跨版本读，英文 key 稳定；中文只是展示。
- 实现：`src/schema.js` 导出 `KIND_LABELS`；`src/panel.js` 的三处下拉与列表文本共用它。新增控件默认名 `新状态/新按钮…`。

## D-U21 使用说明双份同源（0.5.0）

- 决定：正文放 `ui/help.js` 的 `HELP_SECTIONS`（14 节，结构化），面板标题栏 `?` 直接渲染；同时写一份更长的 `docs/使用说明.md`（含示例与表格）给仓库/分享用。
- 理由：扩展不能可靠地 fetch 本地 md（路径、CORS、安装位置都不可控），把要点编译进 JS 才能离线可用；长文留在 docs。
- 约束：两边内容改一处要手动同步；`HELP_SECTIONS` 不写 HTML，渲染端只用 createElement + textContent。

## D-U22 显示名统一为 ILBUI，内部标识不动（0.5.1）

- 决定：用户可见的产品名统一为 **ILBUI**（manifest 的 `display_name`、抽屉标题/aria、帮助首段、README/使用说明标题）。
- 不动：目录名 `dsh-ui`、CSS 前缀 `dshui-`、schema `dshui/1`、存储键 `dshui.layouts.v2`/`dshui.role:*`/`dshui.ui.v1`、导出文件 `kind: dsh-ui`、控制台前缀 `[dsh-ui]`。
- 理由：这些是“标识符”不是“名字”，改了会导致已保存布局、导入文件、安装路径全部失效；品牌名只影响展示。
- 提示：GitHub 仓库名仍为 `dsh-ui`；如需改仓库名，属于平台侧重命名，会影响克隆地址。

## D-U23 编辑全屏、预览铺满视口（0.6.0）

- 决定：编辑态下抽屉正文的浏览件（网格/变量板/页面页签/工具栏/提示）全部让位，编辑器独占整块高度；预览不再是"挤在下面的另一半"，而是铺满整个视口的浮层（`position:fixed` + `100vw`/`100dvh`）。两者彻底不共存。
- 为什么：抽屉只有 360px 宽，编辑器和预览上下分屏时，预览能看到的只是一条窄带，看不出布局在真实页面上的样子；把预览放出去铺满视口，才回答得了"我的界面在聊天页上长什么样"。
- 代价：编辑时看不到预览，要按住/点按按钮切换；拖动条（D-U17）随之作废并删除，`editorHeight` 存储字段不再使用（保留旧键不读，不做迁移）。

## D-U24 预览浮层挂在 root 上，不放进 panel（0.6.0）

- 决定：`.dshui-preview` 是 `.dshui-root` 的子节点，与 `.dshui-panel` 平级；不用 `position:absolute; inset:0`。
- 为什么：panel 上有 `backdrop-filter: blur(6px)` 和 `overflow:hidden`。`backdrop-filter` 会像 `transform` 一样成为 `position:fixed` 的包含块，`overflow:hidden` 会直接裁切——两者叠加的结果是浮层被关回 360×684 的抽屉里（实机量到 `rect=[883,13,360,684]`）。挂到 root 上两者都不生效，量到 `[0,0,1256,708]`（1280×800 视口的真实内容区）。
- 代价：浮层与 panel 之间没有 DOM 从属关系，`ui.destroy()` 要记得同时摘掉 root 下的两个节点；测试里加断言锁住挂载位置，避免以后被"顺手塞回 panel"。

## D-U25 一个预览按钮，长按=临时、点按=锁定（0.6.0）

- 决定：按住 ≥220ms 进入临时预览（松手即回编辑），点一下进入交互预览（再点按钮/浮层「返回编辑」/Esc 退出）。长按松手后浏览器补发的 `click` 由 `peekArmed` 标记吃掉。
- 为什么：两个需求冲突——"我想瞄一眼布局"（不该改变状态）和"我想真的点两下试试"（要留在预览里）。一个按钮用按压时长区分，比并排两个按钮（"看一眼"/"试一下"）更好懂，也不占工具栏宽度。
- 代价：220ms 阈值是经验值，触摸屏上略慢的手指会被判成长按；`LONG_PRESS_MS` 已做成可注入参数（测试用手动计时器），但还没做成用户可配置项。
- 已知边界：进交互预览后工具栏被浮层盖住，工具栏上的按钮此时点不到，退出靠浮层自带按钮或 Esc。

## D-U26 先量再改：P5 以实测审计开工（0.7.0）

- 决定：P5 没有可执行规格（计划里只有一句「手机端只保证不溢出」），所以先写 `tmp/p5audit.mjs` 在真浏览器里量，按量到的数据决定改什么，不按想象改。
- 为什么：第一轮量出来「对比度全部不合格」，差点去改配色；查出是审计脚本自己把半透明背景当不透明算错了（按 alpha 合成后 6.05–13.23，全过 AA）。没有可信的尺子就先动手，改的是幻觉。
- 代价：先花一个审计脚本的成本；但后面每轮改完都能复跑，回归有据可查。

## D-U27 触控目标两档：桌面 28px、触摸 44px（0.7.0）

- 决定：交互控件基线 `min-height: 28px`；`@media (pointer: coarse), (max-width: 640px)` 抬到 `44px`。
- 为什么：28px 已高于 WCAG 2.2 AA 的 24×24 硬下限，桌面用鼠标时紧凑一点能多放内容；触摸屏才需要 44px。媒体查询同时写 `pointer: coarse` 和 `max-width: 640px`：真机命中前者，桌面把窗口拉窄时靠后者兜底，避免只在真机上才生效。
- 代价：手机上 44px 档让抽屉内容变长、需要滚动；桌面和手机两种尺寸的观感不一致，这是有意取舍。

## D-U28 用 `role="group"` 不用 `role="grid"`（0.7.0）

- 决定：网格容器给 `role="group"` + `aria-label="页面：<标题>"`；进度条给 `role="progressbar"` + `aria-value*`。
- 为什么：`role="grid"` 承诺一套键盘导航（方向键在格子间移动、roving tabindex），我们没实现，读屏用户按方向键会没反应——假语义比没语义更糟。`group` 只表达分组，不会诱导错误预期。
- 代价：格子之间不能键盘方向键移动，只能 Tab 逐个走；格子多时 Tab 次数多。

## D-U29 播报挂在 `setMsg()` 上，靠去重防刷屏（0.7.0）

- 决定：面板常驻一个 `.dshui-sr-only`（`role="status"` + `aria-live="polite"` + `aria-atomic="true"`），在 `setMsg(tone, text)` 里调 `announce(text)`；`state.lastLive` 记住上一句，同样的话不重复写。
- 为什么：`setMsg()` 是所有动作结果的唯一出口（点格子、列表项、保存、导入、切页），挂这一个点就全覆盖，不用在十几个回调里各写一遍。去重是因为重绘会反复经过这里，不去重会念到用户想关扩展。
- 代价：只覆盖「结果文案」；变量在别处被改（ILB 其他入口）时不播报，只更新界面。连续快速点击时 `polite` 会排队念，不做合并。

## D-U30 焦点管理只跟 `applyOpen` 走，首屏恢复不抢焦点（0.7.0）

- 决定：`applyOpen(save, moveFocus)` 增加第二参数；开抽屉→焦点进第一个可聚焦控件，关抽屉→焦点回把手；首次加载恢复「上次是打开的」时调 `applyOpen(false, false)`，不动焦点。Esc 做两级：有预览先退预览，没预览才关抽屉。
- 为什么：焦点是键盘和读屏用户的「当前位置」，抽屉开了焦点还在 body 上等于把人扔在原地；但页面刚加载就把焦点抢走会打断用户本来在做的事，所以首屏恢复不算「用户开抽屉」。
- 代价：多一个参数、多两条分支；`collectFocusable()` 自己走 `children` 树（不用 `querySelectorAll`），是为了测试桩能跑同一套逻辑，代码比直接查询长一点。

## D-U31 预览回抽屉里：换的是正文那块地方，不是另开一屏（0.8.0）

- 决定：`.dshui-preview` 改成 `.dshui-panel` 的子节点，排在 `body` 与 `foot` 之间；`flex: 1 1 auto` 吃掉正文的高度。预览时 `body` 整块 `display:none`，标题栏 / 状态行 / 工具栏 / 底栏 / 底栏回执全部留着。
- 为什么（推翻 D-U23、D-U24）：用户要的是「在 ILBUI 的窗口里把界面和编辑器分开」，不是「让界面铺满整个聊天页」。铺满视口那版有三个副作用：① 盖住聊天区，和 D-0003「不打断叙事」的定位相反；② 进了交互预览就够不到布局下拉、状态行和回执，退出只能靠浮层自带按钮或 Esc；③ 手机上等于把整个屏幕让给一张网格，用户没法一边看聊天一边点。
- 为什么仍然互斥：抽屉只有 360px 宽，编辑器和预览上下分屏时谁都看不清；所以是「同一块地方换内容」，不是「同屏各占一半」。
- 代价：预览能看到的宽度就是抽屉宽度，看不出「界面在超宽屏上拉伸」的效果；`D-U24` 记的那套 `backdrop-filter`/`overflow` 包含块坑现在不再需要绕开（预览层本来就要被 panel 裁切），但样式里那句 `position: fixed` 的注释已删，别再写回去。
- 保留：长按临时预览 / 点按交互预览的两段式（D-U25）不变，`peekArmed` 吃掉收尾 click 的逻辑不变。预览栏里的「返回编辑」现在是唯一看得见的退出按钮（`预览` 按钮本身随编辑器一起藏起来了）。

## D-U32 浏览件显隐一律交给 CSS，禁止写内联 display（0.8.1）

- 决定：`renderGrid()` 不再写 `gridBox.style.display`；编辑态只靠 `.dshui-body.is-editing .dshui-grid { display: none }` 这类选择器控制。
- 为什么：0.8.1 用户报「编辑时上面还显示界面」，查下来就是这行内联 `display: grid` —— 内联样式优先级压过类选择器，CSS 那套 `is-editing` 让位规则等于白写。一处内联覆盖让整组规则失效，而且在样式表里完全看不出来。
- 代价：状态类只能挂在父节点上（`body.is-editing` / `panel.is-editing`），不能按需单独藏某一个格子；调试时得去翻 CSS 而不是看 DOM 属性。

## D-U33 面板尺寸跟 `visualViewport` 走，不跟 `100vh`（0.8.1）

- 决定：`applyViewport()` 用 `window.visualViewport` 的 `offsetTop`/`height` 算抽屉的 `top`/`height` 并写内联样式；监听 `visualViewport.resize`/`scroll` 与 `window.resize`；变化不足 32px 忽略；面板关闭时清空内联值。
- 为什么：`100vh` / `100dvh` 描述的是「布局视口」，手机键盘弹起不改布局视口（尤其在 Android），于是抽屉下半截（校验结果、动作条）落在键盘背后，用户既看不到也点不到。`visualViewport` 描述的才是「真正看得见的那块」。32px 阈值是因为地址栏伸缩会连续触发 resize，不设阈值抽屉会持续抖动。
- 代价：多一个全局监听（销毁时一并摘掉）；桌面端 `visualViewport ≈ innerHeight`，等于每次窗口缩放多算一次；iOS 上键盘展开时 `offsetTop` 会变，抽屉可能整体下移一点（已在已知边界记下兜底方案）。

## D-U34 编辑器拆出滚动区，动作条 `flex: 0 0 auto` 吸底（0.8.1）

- 决定：编辑器结构改为 `hint / modeRow / editorScroll(form+textarea+importBox) / issueBox / actions`；只有 `editorScroll` 允许 `overflow: auto`，动作条永不被滚动带走。
- 为什么：动作条原本排在表单流末尾，键盘一挤就被顶出可视区，用户正在改 label 时想点「应用」得先收键盘。吸底之后「输入」和「提交」在视觉上永远是两件事，与 D-U33 配合起来动作条恰好贴在键盘上沿。
- 代价：多一层 DOM；`editorScroll` 必须写 `min-height: 0`，否则 flex 子项不会收缩（这是 flex 布局里最常见的坑，删掉的话滚动区会撑破面板）。

## D-U35 打字时不重建表单：焦点闸 + 结构指纹（0.8.1）

- 决定：`renderForm(force = false)` 两道闸——① 焦点在表单内 `input`/`textarea` 上就 return；② `formKey()`（页码 # 选中项 # 页 id # grid JSON # cells 的 `id:kind` 序列）没变就 return。结构动作（↑↓、删、加页、切页签、点选、填示例、导入）显式传 `force = true`。
- 为什么：用户报「打 label 时光标跳到最前，字成了倒序」。根因是每次重绘都 `clear(formBox)` 重建输入节点，新节点的 `selectionStart` 是 0，往后打的每个字都插在最前面。判「结构」而不是判「值」，是因为值变化（改标题、改数字）本来就只需要更新数据、不需要换 DOM。
- 代价：正在输入时如果别处触发重绘，表单会停在旧值直到失焦后的下一次重绘（网格和变量仍是新的）；结构指纹是字符串拼接，cells 多时每次重绘多一次 `map/join`（64 控件规模可忽略）。

## D-U36 页面与变量收成 chip，浮层不参与布局（0.9.0）

- 决定：页面切换与变量总览默认折叠成两条细 chip（`页面 · 主界面 ▾`、`变量 · 4 ▾`），点开是 `position: absolute` 的浮层；开合状态记进 `dshui.ui.v1` 的 `pagesOpen`/`varsOpen`；两条互斥；点浮层外面 / 选完页面 / Esc 收起。
- 为什么不做成"折叠标题条"（A 方案）：标题条也要占一行、也得配一个箭头，省的高度和 chip 差不多，但 chip 能在同一行放两条（页面 + 变量），A 方案是两行。实测 390×844 下变量区从 132px 降到 28px，网格起点从 336 提到 240。
- 为什么浮层必须绝对定位：如果浮层参与布局流，展开它会把下面的网格顶下去——用户正在点的按钮会跳位，等于"点开变量看一眼"就把界面挪乱了。实测展开前后网格 top 都是 240（delta 0）。
- 为什么用 `pointerdown` 而不是 `click` 判"点外面"：`setPage`/`bump` 会立刻重画，`click` 冒泡到 `document` 时原来的目标节点已经从树上摘掉，`contains()` 必然判 false，浮层会自己关掉。
- 代价：变量特别多时要在浮层里滚动（`max-height: min(46vh, 320px)`）；折叠偏好是全局的，不按布局分别记；chip 只显示当前页名，多页布局要看全貌必须点开。
- 已知边界：单页布局干脆不显示页面 chip（一页没什么可切）。

## D-U37 复制三件套：控件 ⧉、复制页、复制成新布局（0.9.0）

- 决定：三处入口——控件行里加 `⧉`；页面行加`复制页`；动作条加`复制成新布局`。三者都走同一套 `cloneJson` + `freeId`。
- 为什么控件副本要自动下移一行：直接原地复制，副本和原件 `area` 完全重合，校验只给 warning、界面上两格叠在一起，用户第一眼看到的是"没反应"。挪一行至少能看见，重叠了也有校验提醒。
- 为什么"复制成新布局"要先 `delete copy.id`：`store.saveLayout()` 里 `wantId` 优先用传进来的 id，留着原 id 会**覆盖原件**——这是"复制"最不能犯的错。清空 id 才会走"分配新 id"分支。
- 为什么先跑 `validateLayout` 再落盘：复制一个坏草稿进库，等于把错误固化下来；先校验，错了只显示错误列表、不进库。
- 代价：控件副本的默认位置可能仍然与其他控件重叠（只警告不阻止）；复制页时页内 onClick 指向原件页 id 的跳转不会自动改写到副本页；多了一个按钮的宽度，390px 下动作条会多折一行。
