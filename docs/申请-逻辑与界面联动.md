# 申请：让 ILB 逻辑能驱动 ILBUI 的界面（接口增量提案）

> 文档性质：ILBUI 侧向 ILB 侧提出的**接口增量申请**，不是既有契约的重述。
> 申请人：ILBUI（`shayo-yoo/ILB-ui`，当前 v0.8.1，接口契约 `UI扩展接口.md` v1.1）
> 日期：2026-10-27
> 结论先行：我们要的**不是**新事件、不是新数据源、不是读写 lorebook，只是**一个一次性回传通道 + 两条语义确认**。

---

## 一、我们要做什么，为什么绕不开 ILB

ILBUI 的定位是「界面的壳」：它把聊天变量渲染成可点的网格，自己**不做任何求值**——没有表达式、没有脚本、没有定时器。这条是硬红线（决策记录 D-0006），不是能力不足，是刻意的：一旦 UI 侧能求值，用户写的 bug 就会散落在两个扩展之间，谁都说不清。

所以「界面变复杂」这件事，只能靠**ILB 的逻辑当脚本**。这也是 ILBUI 立项时的原始设想：界面负责看得见、点得到；逻辑负责算得对、判得准。

现在已经能做到的部分（v1.1 契约已覆盖）：

| 方向 | 能力 | 状态 |
|---|---|---|
| UI → 逻辑 | `call(name, args)` 跑一条已启用逻辑，`writes` 落盘 | ✅ 已有，够用 |
| 逻辑 → 数据 | `subscribe` / `ilb:change` 让界面跟着变量自动刷新 | ✅ 已有，够用 |
| 逻辑 → **界面行为** | 切页、提示、弹确认、聚焦某项 | ❌ 缺通道 |
| UI → 逻辑（**带上下文**） | 把"用户点的是哪一项、现在在哪一页"作为参数传进去 | ⚠️ 语义不明（见 §三·B） |
| 长逻辑的**进行中**反馈 | 「正在执行…」、耗时、可否取消 | ❌ 缺（同步调用，界面会僵住） |

一句话概括缺口：**逻辑能改数值，但不能改界面；界面能执行逻辑，但不能告诉逻辑"现在是什么情况"。**

---

## 二、我们想要的（按优先级）

### A. 一次性回传通道：`extra.ui`（最重要）

`call()` 现在返回 `{ ok, reason, writes, extra, steps }`，其中 `extra` 在契约里定义为「这次产生的正文」。我们**不想**挪用 `extra` 的语义，而是申请在 `extra` 里**预留一个子键** `ui`，形状由 ILBUI 与 ILB 共同约定：

```jsonc
// call('抽卡') 的返回
{
  "ok": true,
  "writes": { "金币": 90, "卡池结果": "SSR·星轨之刃" },
  "extra": {
    "text": "……原来的正文字段保持不变……",
    "ui": { "v": 1, "page": "结果页", "toast": "SSR！", "select": "card-3" }
  },
  "steps": [ { "idx": 1, "name": "扣费" }, { "idx": 2, "name": "抽卡" } ]
}
```

约定（我们这边全部实现，ILB 侧只需要"原样透传"）：

| 字段 | 类型 | 含义 | ILBUI 的行为 |
|---|---|---|---|
| `v` | number | 指令版本，当前固定 `1` | 不认识就整条丢弃，不报错 |
| `seq` | number? | 可选序号，供去重 | 有则只在变大时执行 |
| `page` | string | 要切换到的页面 id | 存在 `open` 目标就切，不存在就只提示 |
| `toast` | string | 一句话提示（≤80 字） | 写进底栏 + 读屏播报 |
| `select` | string? | 要聚焦/高亮的控件 id | 高亮并滚动到它 |
| `confirm` | object? | 二次确认（`{title, text, ok}`） | 弹确认，确认后才继续后续步骤 |

**关键性质，也是我们为什么想要它而不想要"写变量"：**

1. **一次性**。指令随本次调用返回，不写进聊天状态，不会在下一轮被重新读到，也就不需要"执行完再清空"这种会产生写入抖动的动作。
2. **不污染提示词**。聊天变量会被模型看到；`extra` 不会。界面自己的事不该混进角色卡状态里。
3. **可版本化**。`v` 字段让双方能各自演进；未知字段忽略而不是报错。

**我们承诺的边界**（避免 ILB 侧担心开了一个危险口子）：

- UI 侧**只认上表五个指令**，不做任何字符串求值、不解析表达式、不执行模板；
- 超出长度的 `toast` 截断、未知 `page` 只提示、未知字段静默忽略；
- 指令**只在用户手势触发的 `call` 之后执行一次**，绝不因为重绘重复执行（靠 `seq` 或"每次调用只消费一次"的内存标记）；
- 绝不接受 HTML/CSS/脚本片段。

### B. `call(name, args)` 的参数语义：请给一个确定答案

我们的 `UI扩展接口.md` 第 31 行写的是 `call(name, args)`，交接文档 `交接-UI扩展.md:74` 写的是「`args` 按该逻辑的 `call.params` **顺序**绑定」。两份文档不一致，而这件事直接决定我们能不能做「上下文传参」。

我们要传的通常是这样（**按名**才自然）：

```json
{ "item": "药水-3", "page": "背包", "n": { "$var": "金币" } }
```

请明确其一：

- **按名**（推荐）：`args` 是对象，键与 `call.params` 的 `name` 对齐，缺省用默认值；
- **按序**：`args` 是数组，按 `call.params` 顺序绑定。

如果是按序，我们需要知道 `call.params` 的**形状**（name/type/required），否则只能盲传。**最省事的方案**：`call` 同时接受对象与数组——数组按序、对象按名，我们两边都能吃。

### C. 长逻辑的进行中反馈（可选，但很影响手感）

`call` 目前是同步返回。抽卡这种逻辑如果跑 300ms 以上，界面会整帧僵住，用户看到的是"点了没反应"。

两种都可接受：

1. `call` 返回 Promise / 新增 `callAsync(name, args)`，我们在等待期间把按钮置灰、底栏显示「执行中…」；
2. 或者保持同步，但在返回值里多给一个 `durationMs`，我们至少能在事后告诉用户"这条逻辑用了 800ms，建议精简"。

我们**不需要**进度上报、不需要中断，只要能知道"它还没回来"。

## 三、如果 A 做不到：我们的退路，以及它的代价

如果 ILB 侧不希望动 `extra`（例如它已经是给别的用途预留的），我们会退到「**保留变量信箱**」：

- 逻辑写两个聊天变量：`ui_seq`（整数，每发一条 +1）、`ui_cmd`（JSON 字符串，因为 `vars` 只存标量）；
- ILBUI 在 `subscribe` 回调里比对 `ui_seq`，变了才执行一次，**不回写、不清空**（清空会持续写聊天状态）。

这条路今天就能跑，不需要 ILB 改任何代码。但请 ILB 侧知悉它的两个代价：

1. **聊天变量里会多出两个键**，会被写进提示词。用户和模型都可能看到 `ui_cmd` 里那句"弹窗：确定要删除吗"，挺破坏沉浸感；
2. 状态机变成"计数器 + 字符串"，多一层解析和容错。

**如果走这条路，我们唯一的请求是**：给一个方式让这两个键**不进提示词**（比如约定 `ui_` 前缀默认不注入，或在 `snapshot()` 里标记它们为 `transient`）。只要这一条，退路方案就能接受。

## 四、建议的落地方式（尽量少改 ILB 代码）

按"改动面最小 → 最大"排序，任何一条都够我们开工：

| 方案 | ILB 侧改哪里 | 大致工作量 | 我们能得到 |
|---|---|---|---|
| **1. 原样透传** | `call()` 组装返回值时，若逻辑步骤产出了 `ui` 字段，挂到 `extra.ui` 上，不做任何校验 | 几行 | A 的全部 |
| **2. 专用步骤** | 允许逻辑里写一个 `ui` 步骤（`{ ui: { page, toast } }`），运行时把它收集进 `extra.ui` | 十几行 | A 的全部 + 逻辑作者可读性好 |
| **3. 能力位** | `caps` 里加 `'ui'` 或 `'ui.v1'`，并在 `probe` 里暴露 | 一行 | 我们能按能力开关功能，不用猜版本 |
| **4. 退路** | `snapshot()` 里把 `ui_` 前缀的变量标记为 `transient`（或干脆不注入提示词） | 几行 | 退路方案可用 |

**我们强烈建议顺手加第 3 条**：ILBUI 现在靠 `version` 猜能力（`probe` 里已经处理了 1.0 / 1.1 两档），有了 `caps` 位就能干净地"有就用、没有就退回变量方案"，不必再写版本号比较。

## 五、我们不会要求 ILB 做的事（先说清楚，降低对面的顾虑）

- ❌ 不要求 UI 能读逻辑源码、lorebook 结构、任何内部表；
- ❌ 不要求新事件（`ilb:change` 已够）；
- ❌ 不要求改存储格式或迁移；
- ❌ 不要求 UI 能写 `extension_settings.independent_lorebook`（这是我们自己的铁律第二条，本来就不碰）；
- ❌ 不要求 UI 侧拿到任意执行能力。我们要的最多只是"翻页、提示、聚焦、确认"这四件事。

## 六、最小可验用例（验收标准）

有了 A 之后，下面这条链路应该能跑通，也请 ILB 侧以此为验收：

1. 界面（ILBUI）里点一个按钮 `抽卡`，动作是 `call("抽卡")`；
2. 逻辑内部扣金币、写 `卡池结果`，并在返回时带上 `extra.ui = { v:1, page:"结果页", toast:"SSR！" }`；
3. ILBUI 收到返回后：金币立刻变成新值（靠已有的 `writes` + 订阅），界面**切到「结果页」**，底栏显示 `SSR！` 并被读屏播报；
4. `steps` 能在 ILBUI 的追踪面板里看到走了哪几级（这条现在就能做，不需要新增能力）。

如果这条能跑通，"用 ILB 逻辑当 UI 的脚本"就算成立，剩下的都是我们这边的事。

## 七、优先级与时间

| 项 | 重要性 | 我们的需要程度 |
|---|---|---|
| A. `extra.ui` 透传（或等效通道） | 高 | 没有它，界面只能"跟着变量被动刷新"，做不了分支剧情、结果页、连招确认 |
| B. `args` 语义确认 | 高 | 一句话的事，但决定我们能不能传上下文 |
| C. `durationMs` / 异步 | 中 | 手感问题，可后补 |
| 3. `caps` 能力位 | 中 | 让我们少写版本判断，长期收益大 |

ILB 侧如果有任何顾虑（例如 `extra` 已被占用、或不想让逻辑产出结构化数据），请直接说；我们这边的退路（保留变量信箱）随时能上，只是会牺牲提示词的干净度。**先给个"行/不行/换个形状"的答复就行**，我们按答复决定下一步开发顺序。
