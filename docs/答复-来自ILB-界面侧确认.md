## 1. 你们问的三件小事

### 1.1 `ui.select` 指到不在当前页的控件，自动翻页算不算越界

**不算越界，可以保留。** 但要加一条边界，写成规则就是：

| 指令里有什么 | 界面该做什么 |
|---|---|
| 给了 `page` | 翻到 `page`；`select` **只在这一页上**生效。目标不在这一页 → 只提示一句（「要聚焦的控件不在这一页」之类），**别翻第二页** |
| 只给了 `select` | 允许自己翻到那个控件所在的页再高亮（你们 0.10.0 的做法，我们认可） |
| 两个都没给，只有 `toast` / `ask` | 只提示，不动页面 |

理由和我们上一封说的一致：**书里的逻辑不该依赖"界面的页面布局"这种它看不见的东西**。ILB 不知道哪个页面有什么控件，所以"翻页"必须由写书的人在逻辑里显式写出来（就是 `page` 字段）；`select` 的自动翻页只是兜底——"高亮一个看不见的控件"等于没做，完全禁止反而会让用户以为逻辑坏了。

反过来说：如果作者两个都写了，那就是他自己的明确意图，`page` 赢；如果他只写了 `select` 又抱怨"翻到了别的页"，那是他没写 `page`，我们的文档会教他写。

### 1.2 `ui.toast` 的长度上限

**80 字**，和你们现在的实现一样。而且 ILB 这一侧**在保存阶段就已经截到 80 字**（`core/flow.js` 的 `UI_LIMIT.toast`，`normalizeFlow` 里走 `uiText(raw, 80)`），所以你们那个 `.slice(0, 80)` 正常情况下永远不会触发——是纯兜底。

建议处理方式：**截断 + 省略号**，不要当错误报。理由：上限是"写书时的约束"，应该在作者写的时候就被削平；把已经合法的输入再当异常，只会多一条没人看的警告。

`page` / `select` 的 64 字、`ask.title` 40 / `ask.text` 120 / `ask.ok` 12 同理，都是同一张表 `UI_LIMIT` 管的。

### 1.3 `ui.v = 2` 时能不能带 `deprecated` 之类的字段

**不加，也不建议加。** 我们的方案是让 `v` **逐条演进**，规则三条：

1. **只加字段、不改已有字段语义 → 不升 `v`**。`v: 1` 会一直是 1，你们"不认识的键忽略"就够用了。
2. **只有当老消费方会"做错事"（而不是"看不懂"）时才升 `v`**。升的那天，**能用 `v:1` 表达的指令仍然发 `v:1`**——逐条降级，不整体切换。也就是说：你们永远不会遇到"整批指令忽然全变成 v2"这种事，最多是"某几条新写法的指令你们不认识，忽略掉，其余照常"。
3. **遇到不认识的 `v` 静默忽略就是正确做法**（你们现在就是这样）。

为什么否决 `deprecated`：它要求**读不懂新字段的人**去读懂"新字段里有个标记告诉你旧字段还能用"——凭据反而更少。真正该由 `v` 回答的问题是"我能不能执行这一条"，而逐条版本化已经直接回答了。同理否决"整体升版 + 兼容层"：那会把"什么时候能安全升级"变成全局问题，而它本可以逐条回答。

## 2. 你们提的两条文档建议：都采纳了

1. **"`page` 和 `select` 都是 id，不是标题/文字"** —— 已写死在 `docs/UI扩展接口.md` §4 的字段表里（`page`：「页面 id，不是标题文字——按标题匹配会踩空」；`select`：「控件 id，不是 label/文字」），参考文档 ILB-4.21.10 也记了一条。
2. **"`seq` 的作用域是每个逻辑各自一条"** —— 已写成 ILB-4.21.11，并给了你们一个更好的桶键：**`call` 的返回值从 0.14.1 起带顶层 `id` 与 `name`**：

```js
const r = api.call('抽卡', { 次数: 1 });
// r.id === 'b1::L::1'  ← 分桶就用它（跨书同名时唯一）
// r.name === '抽卡'     ← 给人看，别当键
```

你们原来按**逻辑名**记账，在两个场景会共用一格：① 两本书里有同名逻辑；② 同一本书导出再导入（名字一样、id 不同）。换成 `id` 就没有这个问题。ILB 不校验 `seq` 是否单调、也不替你们去重，`seq` 没填就不出现，按"没有序号"处理即可。

## 3. 我们这边没有变的东西

你们列的"完全照做"四条，我们确认**契约上就是这个意思**，0.14.1 没有放宽任何一条：

- `ui` 里只读数据，**不接受 HTML/CSS/脚本**；字段是白名单，`normalizeFlow` 阶段就截断超长、丢弃未知键，`checkUiNode` 在保存前拦掉 `page`/`select` 里的 `<>"'`\{}`（那些位置是标识符不是文本）。
- **消息触发路径不执行界面指令**：`uiAllowed` 默认 `false`，只有 `api.call` / `callAsync` 传 `true`。被忽略的指令会进 `steps` 的 `reason`（"被忽略（…）：只有用户点按钮调用时才执行"）和返回值的 `uiSkipped` 数组——**你们可以把它当诊断显示出来**，这正是我们希望的"可见的失败"。
- **一次性、不缓存、不重试**：不落盘、不进提示词、不参与重放。
- **一次调用只有一条**：写两个「界面」步骤，只有第一个生效，第二个在 `steps` 里记"已经发过一条界面指令"。

另外补一句我们觉得很关键的：`ui` 是**结果**，不是**权限**。它只说明"这条逻辑想让你做什么"，做不做、怎么做仍然是界面的事（比如 `ask` 只提示不阻塞，`select` 找不到控件就只提示）。这条写进了 ILB-4.21.3 的收尾。
