## 一、先纠正三处与 ILB 现状对不上的地方

这三条不改，后面的方案会建在错误前提上。其中第 2 条是**你们手上那份交接文档是旧版**，不是现状。

### 1. B（`args` 语义）：已经是"按名"，不需要再确认

`args` 是**对象**，键为逻辑里声明的参数名，**不是数组、不是顺序**。这条在 1.1 就已经实现并写进契约（`UI扩展接口.md:89`）：

- 代码里传数组会直接返回失败：`{ ok:false, outcome:"error", reason:"args 要传对象（键是参数名），不是数组" }`；
- 正常返回带 `unusedArgs`（传了但逻辑没声明）与 `missingParams`（逻辑声明了但没传），你们可以据此做即时提示；
- 参数名的来源就是你们已经在用的 `snapshot().books[].logics[].params`（1.1 新增）。

**关于"两份文档不一致"**：`交接-UI扩展.md:74` 的"按顺序绑定"是 **v0.11.1 的旧文本**；v0.12.0（提交 `a6213e8`）重写接口时就改成了"`args` 是**对象**，键是 `call.params` 里的参数名（**按名绑定，不是按顺序**）"，现在仓库里的 `docs/交接-UI扩展.md:75` 与镜像副本都是这个写法。请 `git pull` 到 v0.13.2 后再看一遍——如果你们看到的仍不一致，请把那份文件的提交号发我们。

**关于"同时接受对象与数组"**：不加。1.1 刚把"传错类型静默成功"改成显式失败（决策 D-0049），两套语义并存等于把修好的东西退回去。请按对象传，传错我们报错并告诉你们缺哪个参数——这比静默猜顺序对你们更省事。

### 2. 能力位（你们的第 3 条）：容器已有，只差一个条目

`caps` 不是新机制。1.1 起 `api.caps`（数组）、`describe().caps`、`ilb:ready` 事件的 `detail.caps` 三处都在，现有条目：`snapshot / set / remove / call / subscribe / outcome / byId / nonce / context / strict / vars / caps`。

所以你们要的只是**再加一个 `'ui'`**，一行的事。**不用再靠 `version` 猜能力**，从"有 `caps` 但没 `ui`"就能干净地退回变量方案。

### 3. `extra` 的类型：v1.1 里它是 `string[]`，不是 `{text}`

你们样例里假设 `call()` 返回的 `extra` 是个对象、里面有 `text` 字段。实际契约是：`extra` 是**字符串数组**，表示"本次产生的正文"（由逻辑里的「添加」「输出」节点收集，`core/flow.js:578`、`core/flow.js:631`）。

这不是措辞问题，而是**语义冲突**：`extra` 已经是"给聊天看的内容"，再让它装"给界面看的指令"，两件事会挤在一个字段里，将来谁都说不清哪个该给谁。所以见下节。

## 二、A 的形状：`ui` 放顶层，由专用步骤产出

### 2.1 返回值形状

```jsonc
// api.call('抽卡') 的返回
{
  "ok": true,
  "outcome": "ok",                 // ok | blocked | error（1.1 已有）
  "ran": true,
  "passed": true,
  "reason": "",
  "writes": { "金币": 90, "卡池结果": "SSR·星轨之刃" },
  "extra": ["……原来的正文数组，一个字符都不变……"],
  "ui": {                          // ← 新增：这次要界面做什么；没有就是 null
    "v": 1,
    "seq": 7,                      // 可选，逻辑侧单调递增，供你们去重
    "page": "结果页",
    "toast": "SSR！",
    "select": "card-3"
  },
  "durationMs": 41,                // ← 新增：本次执行耗时（实测值，非估算）
  "steps": [ { "idx": 1, "name": "扣费" }, { "idx": 2, "name": "抽卡" } ],
  "vars": { "...": "..." },
  "unusedArgs": [],
  "missingParams": []
}
```

为什么放顶层而不是 `extra.ui`：

1. `extra` 有既定类型（`string[]`）和语义（正文）。改它=破坏性变更，你们和别的消费者都得改。顶层加字段是**纯加法**，不认识 `ui` 的旧代码完全无感。
2. 两个字段各自演进：正文可以变长、可以多条；界面指令是有限几个键，校验规则完全不同。混在一起会让校验变得难看。
3. 版本号天然落在 `ui.v` 里，和 `caps: ['ui']` 配套：没有 `'ui'` 就当没有这个字段。

### 2.2 谁来产出：一个「界面」步骤，不是原样透传

我们不接受"逻辑里随便吐个对象就原样传给界面"。原因：透传等于**任何字符串都能变成界面指令**，作者自己都说不清他在发什么，出了事也无法定位。

改成：逻辑里加一种节点类型「界面」——

```jsonc
// 表单模式：勾选项 + 输入框
{ "type": "ui", "ui": { "v": 1, "page": "结果页", "toast": "SSR！", "select": "card-3" } }

// 文本模式：一行
界面 结果页 "SSR！" 聚焦 card-3
```

这样做的收益：

- **保存时校验，而不是运行期**。白名单键（`v/seq/page/toast/select/ask`）、长度上限（`toast` ≤ 80 字、`page`/`select` ≤ 64 字符）、`v` 必须是 `1`、拒绝 HTML/CSS/脚本片段；写了不认识的键、超长、`v` 不对 → 立刻在编辑器里报错，不落盘。
- **可读**。作者打开逻辑就能看出"这一步会让界面翻到结果页"，而不是埋在一个 JSON 字符串里。
- **不触碰 D-0006**。「界面」步骤是**数据**，不是表达式，没有求值、没有拼接、没有条件。与「添加」「激活」同级。
- **一次调用只发一条**。多条会互相覆盖、还会产生"先翻页再提示"的时序问题；需要多条就调两条逻辑（或分两步逻辑），语义清晰。

### 2.3 `ui` 里我们允许的键（就这几个，不再扩）

| 键 | 类型 | ILB 侧校验 | 你们的处理 |
|---|---|---|---|
| `v` | number | 必须 `1`，否则整条丢弃 | 不认识就整条丢弃，不报错 |
| `seq` | number? | 非负整数 | 只在变大时执行 |
| `page` | string | ≤ 64 字符 | 切换到该页；没有这个页就只提示，不报错 |
| `toast` | string | ≤ 80 字符 | 底栏提示 + 读屏播报 |
| `select` | string? | ≤ 64 字符 | 高亮并滚动到该控件 |
| `ask` | object? | `{ title≤40, text≤120, ok≤12 }` | **只提示、不阻塞**（原因见下节） |

## 三、`confirm` 在现有运行时上不成立

你们的定义是「弹确认，确认后才继续后续步骤」。这个语义**没法实现**，原因是执行顺序：

`call` 是**同步跑完整条逻辑**才返回的（`runtime/api.js:203` 是普通函数，不是 async）。等 ILBUI 拿到 `ui.confirm` 时，扣费、写结果**已经落盘了**——此时"继续后续步骤"已经没有后续步骤可继续。要做成真的"中途暂停等确认"，运行时必须变成**可挂起、可续跑**（逻辑执行到一半存下位置、等界面回执再恢复）。那是另一个量级的改动，会让"逻辑什么时候跑完"变得不可预测，也会破坏现在"一次调用＝一次完整结果"的简单心智。**我们不做。**

两个可行的替代，都不需要 ILB 改运行时：

**替代一：拆成两条逻辑（我们推荐）**

- `抽卡-预检`：只计算、不写（或不写关键字段），返回 `ui = { v:1, ask:{ title:"确认抽卡？", text:"消耗 10 金币", ok:"确定" } }`；
- ILBUI 用**自己的按钮**弹确认（这是界面的事，本来就该界面做）；
- 用户点"确定" → ILBUI 再 `call('抽卡-提交')` → 这条真扣费、写结果，返回 `ui = { v:1, page:"结果页", toast:"SSR！" }`。

好处：零新增能力、两次调用都可追踪、用户点取消就什么都不发生（不需要"撤销"）。

**替代二：`ask` 只提示不阻塞**

保留一个 `ask` 字段，但它只是"弹一条带确定按钮的提示"，不承诺任何后续步骤。适合"你已经抽完了，要去看吗"这种。

**请你们选一个**（或者两个都实现：预检/提交用于真确认，`ask` 用于纯提示）。我们默认按替代一写验收用例。

## 四、C（同步阻塞）：给 `callAsync`，不动 `call`

`call` 保持同步返回对象（**兼容第一批已经写好的代码**），新增：

```js
const r = await api.callAsync('抽卡', { /* args */ });
// 行为等价于 call，区别只有三点：
//   1. 跑之前先让出一帧，你们能先把按钮置灰、底栏写「执行中…」；
//   2. 返回里带 durationMs；
//   3. 从不抛异常（失败也是 resolve，看 outcome）。
```

`durationMs` 同时会加进同步的 `call` 返回值里，方便你们事后统计"这条逻辑太慢，建议精简"。

我们不会做进度上报、不会做中断——按你们说的，只要知道"它还没回来"就够。

## 五、关于你们的退路（保留变量信箱）：可以，但那层顾虑是多余的

你们在 §三 提的退路（`ui_seq` + `ui_cmd` 两个聊天变量）技术上可行，我们不会阻止。但要纠正一个前提：

**ILB 的变量不会自动进提示词。** 只有当某条条目正文里真的写了 `{{ILB:chat.ui_cmd}}` 时，那一轮才会被展开进去（`runtime/pipeline.js:187` 做宏展开，`core/vars.js:75` 实现）。没有引用＝不会出现。所以"用户和模型都会看到 `ui_cmd` 里那句弹窗文案"这件事，只要没有人真的去引用它，就不会发生。

因此：

- **我们不加 `transient` 机制**。多一个"某些变量特殊"的概念，就要在状态页、快照、宏展开、导出、导入五处都加特例，收益不匹配。
- 我们能做的最小让步：**状态页把 `ui_` 开头的变量单独折叠成"界面通道"一栏**，让用户一眼看出这不是剧情变量。仅此而已。
- 提醒一句实现风险：那条路**每轮都要写 `chatMetadata`**。抽卡这种低频没问题，别做成每次重绘/每次订阅回调都写——那会变成持续写盘。

如果走这条路，请在你们文档里注明"该通道的变量不保证被清理、不保证顺序"，免得将来当作正式契约依赖。

## 六、一条我们要求写进契约的安全约定

**`ui` 指令只能由"用户手势触发的 `call` / `callAsync`"产生并执行；绝不能在消息时间（AI 回复触发激活）路径上产生。**

理由：世界书可以从别人那里导入。一旦"消息触发 → 激活 → 界面指令"这条链成立，一本别人写的书就能在你的界面上弹框、自动翻页、自动聚焦，甚至用 `ask` 的文案做社会工程（"确定要删除吗"实际执行的是别的事）。这是真实攻击面，不是理论顾虑。

具体到实现：

- ILB 侧：`ui` 只在 `api.call` 的返回里出现；常规激活（`evaluate` 流程）即使遇到「界面」步骤也只**收集不执行**，并写一条诊断日志（"界面步骤被忽略：不在调用路径上"）。
- ILBUI 侧：收到 `ui` 后**只对本次用户手势执行一次**，绝不因重绘重放（用 `seq` 或"每次调用只消费一次"的内存标记，你们方案里已经写了，很好）。
- 双方共同：拒绝 HTML/CSS/脚本片段；未知字段静默忽略；超长截断而不是报错。

## 七、验收用例（按我们的形状改写）

1. ILBUI 里点按钮「抽卡」，动作是 `api.callAsync('抽卡', {})`；
2. 逻辑内部：比较金币 → 扣费（写 `金币`）→ 写 `卡池结果` → 「界面」步骤 `{ v:1, page:"结果页", toast:"SSR！", select:"card-3" }`；
3. ILBUI 收到返回后：金币立即变成新值（走已有的 `writes` + 订阅）；界面**切到结果页**；底栏显示 `SSR！` 并被读屏播报；`card-3` 高亮；
4. `steps` 在追踪面板里能看到走了哪几步；`durationMs` 显示耗时；
5. 反向用例：把 `v` 改成 `2` → 整条 `ui` 被丢弃、界面不动、不报错；把 `page` 写成不存在的页 → 只提示、不切换；
6. 反向用例：一条**消息触发**的逻辑里放「界面」步骤 → 界面完全不动，诊断页出现"界面步骤被忽略"。

第 5、6 条是我们回归测试里会长期保留的。
