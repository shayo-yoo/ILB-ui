## 1. 两个问题的答复

### 问题一：`ui` 放顶层还是 `extra.ui`

**采纳顶层 `ui`。**

同意你们的理由，并补一条我们这边的原因：`extra` 在 v1.1 契约里的语义是「本次产生的正文」，是**给人看**的文本，形状是 `string[]`。如果把控制指令塞进 `extra`，等于让「显示什么」和「做什么」共用一个字段——将来 `extra` 规范化成纯字符串数组时，指令会被加工层的 `String()` 静默吃掉。

实现上我们还加了一道门禁：**先看 `caps` 有没有 `'ui'`，再要求 `ui.v === 1`**，两条都过才认。`v` 不认识就当没有（静默忽略，不报错）。这样即使有人手写一个 `{ui:{...}}` 塞进不该塞的地方，也不会被界面执行。

### 问题二：`confirm` 的三选

**选替代二：`ui.ask` + 拆两条逻辑。** 不要「两个都要」。

理由和你们一致：`call` 已经返回了，此时界面再摆一个「确定/取消」框，是**假装同步**——用户点「取消」时没有任何代码在监听，那是骗人的交互。所以我们只做「一次性提示」，不拦任何操作。

二次确认的落地写法是拆成两条逻辑：

| 按钮 | 调的逻辑 | 逻辑做什么 |
|---|---|---|
| 「确认使用」 | `检查-使用` | 只判断，返回 `ui.ask`：`{title:'还差 2 点体力', ok:'知道了'}` 或「再点一次才生效」 |
| 「真的使用」 | `使用` | 真正扣体力、写变量 |

也就是说：**确认的语义由逻辑拆成两步承担，界面只负责把话说清楚**。这条我们写进了使用说明第 16.5 节和面板内帮助。

## 2. 我们对契约的实现（已发布）

| 能力 | 我们的实现 |
|---|---|
| `ui.toast` | 顶替底部那句回执；截 80 字 |
| `ui.page` | 按**页面 id**切页；id 不存在只提示「没有这一页」，不切、不报错（按你们要求） |
| `ui.select` | 按**控件 id** 给格子描边 + `scrollIntoView` |
| `ui.ask` | 底部卡片 `{title,text,ok}`；不阻塞、不抢焦点 |
| `ui.seq` | 按**逻辑名**记账，只严格变大才执行；只存内存，刷新后清零 |
| `callAsync` | 有就走异步，点完先显示「执行中…」；没有退回同步 `call` |
| `durationMs` | 显示在回执里（如 `37ms`） |
| `caps:'ui'` | 状态行末尾显示 `· ui`，用户一眼看到通道开了 |

**额外做了一件事，请你们确认算不算越界**：`ui.select` 指到的控件如果**不在当前页**，我们会先翻到它所在的页再高亮。理由是「高亮一个看不见的控件」等于没做；但如果你们认为 `select` 不该引起页面变化，我们就改回「只在当前页找，找不到就只回执一句话」。

## 3. 对契约的两条反馈

1. **建议在文档里写死「`page` 和 `select` 都是 id，不是标题/文字」**。现在只写了「页面 id」，`select` 那句容易被人理解成「label」。我们已经按 id 实现，改标题的人会踩坑。
2. **`seq` 的作用域建议写成「每个逻辑各自一条」**。我们按逻辑名记账；如果将来出现「逻辑重名 + 用 id 调用」的场景，两条逻辑会共用一格 seq。你们文档里如果明确「seq 由逻辑自己维护、与逻辑一一对应」，我们这边就不用额外按 id 分表。

另外确认你们这几条我们**完全照做**了：不接受 HTML/CSS/脚本（`ui` 里只读数据）；消息触发路径不执行界面指令（我们只在用户点按钮的调用里消费 `ui`，`ilb:change` 事件只用来重画变量）；`ui` 是一次性的、不缓存、不重试。
